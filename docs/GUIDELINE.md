# Нативный клиент для сайта: гайдлайн, план и промпт

Nov 15, 2026 · @Sergei

## 1. Цель и границы

Цель: десктопный клиент под Linux, который открывает живой сайт игры «Легион» (legiongame.gg), быстрее его запускает и обновляет данные, а также позволяет подключать патчи, меняющие интерфейс и логику самого сайта. Проект для личного использования.

**Входит в проект**

- Оболочка на Electron, которая загружает `/c/<канал>/` и сама получает обновления сайта.
- Слой перехвата запросов и дисковый кэш неизменяемых файлов.
- Движок патчей: подключение, самопроверка, откат, отчёт; доступ патчей к внешним адресам, в том числе к вашему серверу (раздел 5).
- Мультиаккаунт как отдельные сессии Chromium плюс патч с переключателем.
- Нативные функции: трей, уведомления, горячие клавиши, настройки GPU.
- CI, который проверяет патчи на новых версиях сайта.

**Не входит**

- Полный клон игры и офлайн-режим: сервер определяет состояние игры, а бэкенда у нас нет.
- Собственный бэкенд или подмена серверных ответов.
- Автоматизация игровых действий: боты, автокликеры, автоторговля.

**Принципы**

- Сайт остаётся источником истины. Любой патч может отвалиться, и тогда сайт работает как без него.
- Патчи меняют интерфейс, скорость и уведомления, но не действуют вместо игрока.
- Всё отключается одним флагом (safe mode).
- Перед включением мультиаккаунта прочитать правила игры (`/rules`). Обмен предметами между своими аккаунтами не делать, пока правила не проверены.

## 4. Структура репозитория

Стек: TypeScript (strict), актуальный стабильный Electron на момент старта, pnpm, vitest для юнит-тестов, Playwright для e2e. Код патчей лежит отдельно от ядра, чтобы добавление нового патча сводилось к новой папке.

```text
lg-native/
├─ package.json, tsconfig.json, .gitignore
├─ docs/
│  ├─ GUIDELINE.md        этот документ
│  ├─ PATCHES.md          как писать патчи
│  └─ DECISIONS.md        журнал архитектурных решений
├─ src/
│  ├─ main/               процесс Electron main
│  │  ├─ app.ts           запуск, флаги (safe mode, GPU)
│  │  ├─ accounts/        сессии, окна, хаб
│  │  ├─ net/             перехват запросов, кэш, проверка версии
│  │  ├─ patching/        движок патчей
│  │  ├─ native/          трей, уведомления, хоткеи
│  │  └─ ipc/             белый список каналов
│  ├─ preload/            мост contextBridge, ранние хуки
│  ├─ runtime/            код в мире страницы: API LGX
│  └─ shared/             типы, схема манифеста, константы
├─ patches/
│  ├─ _template/          шаблон нового патча
│  └─ <patch-id>/
│     ├─ patch.json       манифест
│     ├─ index.ts         код патча
│     ├─ README.md        что делает, на что опирается, как проверить
│     └─ test.ts          тест на фикстурах
├─ tools/
│  ├─ snapshot/           сборщик снапшотов (перенести существующий)
│  └─ dryrun/             сухой прогон патчей на снапшоте
├─ fixtures/snapshots/<site_ver>/   эталонные файлы сайта по версиям
└─ tests/                 интеграционные и e2e
```

Правило границ: `main` и `preload` ничего не знают о конкретных патчах, а патчи не импортируют ничего из `main`. Связь только через манифест и API LGX.

## 5. Патч-система

Патч = папка `patches/<id>/` с манифестом `patch.json`, кодом, README и тестом. Новый патч должен добавляться копированием `_template` без правок ядра.

### Типы патчей

| Тип | Где работает | На что опирается | Устойчивость к обновлениям сайта |
| --- | --- | --- | --- |
| `css` | Страница, при старте | Селекторы и переменные стилей | Высокая |
| `runtime` | Мир страницы, после загрузки модуля | Публичные объекты (`LGQuest`, `LGTrade` и др.) и браузерные API | Средняя или высокая |
| `source` | Цепочка перехвата: текст файла меняется перед отдачей странице | Якорь (точный фрагмент кода) и имя файла | Средняя, по умолчанию строгий режим |
| `ast` | Та же цепочка | Поиск функции по структуре в дереве разбора | Средняя, устойчивее текстового якоря |
| `native` | Процесс `main` | Только API Electron и события из LGX | Не зависит от сайта |

### Манифест `patch.json`

```json
{
  "id": "fast-me-cache",
  "name": "Быстрый старт из кэша /api/me",
  "version": "0.1.0",
  "type": "runtime",
  "enabled": true,
  "siteVersions": ["2c1ee071d4"],
  "strict": false,
  "scope": { "channels": ["*"], "pages": ["/c/*"] },
  "targets": [{ "file": "/site/app.js", "anchor": "...", "expect": 1 }],
  "requires": ["global:LGLive", "global:LGQuest"],
  "onFail": "disable",
  "settings": { "ttlMs": 5000 }
}
```

- `siteVersions`: версии сайта, на которых патч проверен. `strict: true` означает, что на других версиях патч не применяется. Для `source` и `ast` это значение по умолчанию.
- `targets`: для `source` и `ast`. `expect` — точное число совпадений якоря; иначе файл отдаётся без изменений.
- `requires`: признаки, которые должны существовать (`global:`, `selector:`, `file:`). Нет признака — патч не запускается.
- `onFail`: `disable` отключает патч до перезапуска, `original` отдаёт оригинальный файл.

### Требования к патчу

1. Идемпотентность: повторный запуск не дублирует действия.
2. Исключения не выходят наружу: движок ловит их, отключает патч и пишет причину в отчёт.
3. Патч объявляет всё, на что опирается (`requires`, `targets`).
4. Патч в мире страницы работает только через LGX, без доступа к Node.
5. Все логи с меткой `id` патча; любой патч можно выключить без пересборки.

### Предлагаемый API `window.LGX`

| Вызов | Для чего |
| --- | --- |
| `LGX.version()` | Версия сайта и имя аккаунта |
| `LGX.expose(name, value)` | Публикация внутренностей из `source`-патчей (например `api`, `ME`, `apply` из `app.js`) |
| `LGX.get(name)` | Чтение опубликованного |
| `LGX.hook(obj, method, wrapper)` | Безопасная обёртка метода с откатом при ошибке |
| `LGX.ready(feature, timeoutMs)` | Ожидание появления глобала или селектора с таймаутом |
| `LGX.on(event, fn)` / `LGX.emit(event, data)` | Шина событий: live-события, смена вкладки, смена аккаунта |
| `LGX.settings(patchId)` | Настройки патча из `patch.json` и пользовательских переопределений |
| `LGX.log(patchId, ...args)` | Структурный лог в общий журнал |
| `LGX.native.notify(...)`, `LGX.native.openWindow(...)` | Мост к `main` через белый список каналов |

Это начальный набор; недостающие вызовы добавляются по мере нужды патчей, с записью в `DECISIONS.md`.

### Доступ патчей к внешним адресам

Патч может получать данные с других адресов, например с вашего сервера. Запросы идут не из страницы, а через `main`, поэтому их не ограничивают CSP сайта и CORS. Это дополнение к API LGX выше.

- Вызов: `LGX.net.fetch(url, options)` в мире страницы. `main` выполняет запрос через `net.fetch` и возвращает статус, заголовки и тело.
- Белый список: хосты, к которым патч имеет право обращаться, объявляются в манифесте в поле `network.hosts`. Запрос к другому хосту отклоняется и записывается в отчёт патча.
- Только HTTPS (для `localhost` в режиме разработки допускается HTTP). Таймаут и лимит размера ответа задаются в `network`, по умолчанию 10 секунд и 2 МБ.
- Адрес вашего сервера хранится в настройках профиля (`serverUrl`), в манифесте его можно указать как `"$serverUrl"`, и он подставится из настроек.
- Cookie и заголовки авторизации игры в такие запросы не добавляются. Токен для вашего сервера хранится в настройках приложения (через `safeStorage`), не в коде патча и не в репозитории.
- Что именно патч отправляет на ваш сервер, он описывает в своём README. Данные других аккаунтов и содержимое `/auth/*` не отправляются.
- Ответ сервера считается данными, а не кодом: его нельзя исполнять и подставлять вместо файла сайта без проверки хэша или подписи.

```json
"network": {
  "hosts": ["$serverUrl", "api.example.com"],
  "timeoutMs": 10000,
  "maxBytes": 2097152
}
```

## 6. Перехват запросов и кэш

Все запросы к `legiongame.gg` проходят через один обработчик в `main` (`session.protocol.handle`). Это даёт две вещи: дисковый кэш и точку для `source`-патчей.

| Тип запроса | Поведение |
| --- | --- |
| Файл с `?v=<хэш>` | Кэш на диск по полному URL. Хранится оригинал и результат патчей (ключ: хэш оригинала + набор патчей + их версии) |
| `/index.html` канала, `/site/ver` | Сеть с коротким таймаутом; при ошибке допускается последняя закэшированная копия |
| `/api/*`, `/auth/*`, `/ws`, SSE | Только сеть, передача без изменений. Запросы можно только наблюдать (лог, замеры) |

Запросы патчей к другим адресам (например, к вашему серверу) этот обработчик не затрагивает: они идут отдельным путём `LGX.net.fetch` через `main` и проверяются по белому списку хостов (раздел 5).

**Правила**

- `cookie` и заголовки авторизации не трогать, `User-Agent` не менять без необходимости.
- При старте запрашивать `/site/ver` и сравнивать с последней известной. При смене пересчитывать применимость патчей и записывать это в отчёт.
- Кэш очищается по возрасту и объёму (задаётся в настройках).
- Показ закэшированного состояния `/api/me` до прихода свежего (stale-while-revalidate) делается патчем, а не ядром, отдельно для каждого аккаунта и только для чтения.

**Что проверить до начала работы (этап 0)**

- Не ломает ли `protocol.handle` WebSocket, SSE и OAuth-редиректы. Если ломает, альтернатива — без перехвата для этих путей и патчи только через preload.
- Действительно ли хэш в `?v=` меняется вместе с содержимым файла. Проверить по двум снапшотам разных версий.

## 7. Мультиаккаунт

Мультиаккаунт нельзя реализовать патчем внутри страницы: серверная сессия держится на HttpOnly-cookie, а она одна на сессию браузера. Поэтому ядро даёт механизм, а интерфейс переключения добавляется патчем.

- **Аккаунт** — профиль `{id, имя, partition, канал по умолчанию}`. Partition = `persist:acc-<id>`, поэтому cookie и `localStorage` у аккаунтов не пересекаются.
- **Представление** — отдельное `WebContentsView` (или окно) на каждый аккаунт со своим WS. Внешние ссылки открываются в системном браузере.
- **Фон.** Для активных аккаунтов отключается `backgroundThrottling`, чтобы WS не замирал. Лимит одновременно живых аккаунтов задаётся настройкой, остальные запускаются лениво.
- **Хаб** (в `main`): реестр аккаунтов, активный аккаунт, общий трей и уведомления с меткой аккаунта, шина событий между представлениями через IPC.
- **Переключатель** — патч `runtime`, который вызывает `LGX.native.*`; сам он ничего не знает о partition.
- **Вход.** Twitch OAuth проходит в окне самого аккаунта. Нужно проверить на этапе 0; если Twitch не пустит, запасной путь — вход через системный браузер с возвратом в приложение.

**Границы**

- Никаких действий от имени аккаунта без явного действия пользователя.
- Пароли и токены не хранятся нами: только сессии Chromium в каталоге профиля с правами только для владельца.
- Передача предметов и ресурсов между аккаунтами не реализуется, пока правила игры не проверены (раздел 1).

## 8. Совместимость с обновлениями сайта и CI

Сайт может обновляться в любой момент, поэтому надёжность держится на трёх вещах: патчи не доверяют сайту слепо, отказ одного патча не влияет на остальные, а поломка обнаруживается раньше запуска.

**В клиенте (на каждом запуске)**

| Ситуация | Что применяется |
| --- | --- |
| Версия сайта известна и есть в `siteVersions` патча | Патч применяется полностью |
| Версия новая, патч `css`, `runtime` или `native` | Применяется, если прошли признаки `requires` |
| Версия новая, патч `source` или `ast` | Не применяется, пока версия не подтверждена сухим прогоном; с `strict: false` применяется, если якорь совпал ровно `expect` раз |
| Якорь не найден или найден не такое число раз | Файл отдаётся оригиналом, патч помечается `failed` |
| `/site/ver` недоступен | Работаем по последней известной версии, `strict`-патчи отключены |

**В CI (раз в сутки)**

1. `tools/snapshot` забирает файлы сайта и сравнивает с предыдущим эталоном в `fixtures/snapshots/`.
2. `tools/dryrun` прогоняет все `source` и `ast` патчи на новых файлах: найден ли якорь, сколько раз, валиден ли результат как JavaScript.
3. Playwright открывает публичные страницы без входа и проверяет `requires` для `runtime`-патчей.
4. Результат — отчёт «патч × версия» (`ok` или `fail` и причина). При `fail` патч добавляется в список отключённых для этой версии.
5. Проверки за авторизацией делаются локально через само приложение (режим `--selftest`). Cookie в CI и репозиторий не попадает.

Доставка патчей с удалённого сервера не нужна, пока проект для личного использования: патчи берутся из локальной папки `patches/`. Если понадобится, удалённая доставка добавляется с проверкой подписи или SHA-256.

## 9. Этапы и критерии приёмки

Основа проекта и основа для патчей — этапы 0–2. Этапы 3–5 идут после них, каждый со своим приёмочным тестом. На следующий этап не переходим, пока критерий предыдущего не выполнен.

| Этап | Что делаем | Критерий приёмки |
| --- | --- | --- |
| 0. Разведка | Electron грузит `/c/<канал>/`; проверяем вход через Twitch, WS и SSE, Pixi, звук, popup; меряем базовые показатели; добираем снапшот | Вход проходит, WS подключается, Pixi рисует; в `docs/BASELINE.md` записаны время до интерактивности и задержка событий |
| 1. Каркас и перехват | Окно, профиль, `protocol.handle`, дисковый кэш `?v=`, проверка `/site/ver`, логирование | Повторный запуск не скачивает файлы с `?v=`; WS, SSE и вход работают; время до интерактивности не хуже базового |
| 2. Движок патчей | Манифесты, схема и валидация, типы `css`, `runtime`, `source`, API LGX, отчёт, safe mode, `_template`; три примера (css, обёртка метода, expose из `app.js`) | Патч включается и выключается без пересборки; сломанный якорь даёт оригинальный файл и запись в отчёте; тесты на фикстурах зелёные |
| 3. Мультиаккаунт | Сессии, представления, хаб, переключатель-патч | Два аккаунта одновременно, cookie и `localStorage` изолированы, WS жив в фоне |
| 4. Нативное и производительность | Трей, уведомления, хоткеи, флаги GPU, лимит FPS в фоне, профилирование | Замеры «до и после» в `docs/BASELINE.md` по каждой оптимизации |
| 5. CI и сухой прогон | `tools/snapshot`, `tools/dryrun`, суточный отчёт | На новой версии сайта сломанный патч виден в отчёте и не применяется |

**Общее условие готовности этапа:** тесты зелёные, код проходит проверку типов и линтер, новые решения записаны в `DECISIONS.md`, у каждого патча есть README.

## 10. Гайдлайн по коду, тестам и логированию

**Безопасность Electron**

- `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true` для всех окон с чужим содержимым.
- Preload даёт только узкий мост (`contextBridge`) с белым списком IPC-каналов; каждый канал проверяет аргументы.
- Навигация ограничена origin’ом игры и доменами входа Twitch; остальные ссылки открываются в системном браузере.
- Код из сети не выполняется без проверки SHA-256 или подписи. Манифесты валидируются схемой (zod или JSON Schema).

* Запросы патчей наружу идут только через `LGX.net.fetch`: белый список хостов, HTTPS, таймаут и лимит размера, без cookie игры.

**Код**

- TypeScript strict, без `any` в `main` и `shared`.
- Каждый патч выполняется в `try/catch`. Сбой отключает этот патч и пишет причину; приложение не падает.
- Маленькие модули с одной ответственностью; без глобального состояния вне явных объектов (`AccountHub`, `PatchEngine`, `CacheStore`).
- Конфигурация в одном файле профиля со схемой и значениями по умолчанию.

**Тесты**

- Юнит-тесты движка: якорь найден / не найден / найден несколько раз, идемпотентность, порядок применения, откат. Фикстуры — файлы из `fixtures/snapshots/`.
- У каждого патча минимум один тест: «включён на фикстуре — результат получен» и «якорь отсутствует — файл не изменён».
- После правки файла `source`-патчем результат проходит синтаксическую проверку (разбор как JavaScript) до отдачи.
- e2e: один smoke-тест приложения на Playwright или Electron-драйвере: запуск, загрузка страницы, применённый патч.

**Логи и отчёты**

- Структурные логи (JSON-строки) с полями `patchId`, `siteVer`, `account`; ротация по размеру.
- В логи не попадают cookie, токены и тела запросов к `/auth/*`.
- Отчёт патчей пишется при каждом запуске в отдельный файл и доступен через пункт трея.

**Работа в репозитории**

- Маленькие коммиты, один патч — один коммит или PR.
- README патча: что делает, на что опирается, как проверить вручную, как выключить.
- Архитектурные решения — в `docs/DECISIONS.md` короткими записями: контекст, решение, последствия.
- Секреты, cookie и профили браузера в `.gitignore`.

## 11. Риски и открытые вопросы

| Риск | Что делать |
| --- | --- |
| Twitch не пускает во встроенное окно | Проверить на этапе 0. Запасной путь: вход в системном браузере с возвратом в приложение |
| `protocol.handle` ломает WS, SSE или редиректы | Исключить эти пути из перехвата; патчи для них только через preload |
| Хэш в `?v=` не гарантирует неизменность файла | Сравнить два снапшота разных версий; кэшировать по хэшу содержимого, если не совпадает |
| Снапшот неполный | На этапе 0 добрать 6 недостающих файлов с `?v=`, определить какие из них ленивые модули |
| Патчи ломаются при каждом обновлении `app.js` | Маленькие якоря, предпочтение `runtime`-обёрткам на публичных объектах, сухой прогон в CI |
| Правила игры запрещают модификацию клиента или мультиаккаунт | Прочитать `/rules` и `/legal/terms`; если неясно — спросить администрацию игры до включения |
| Рост потребления памяти при нескольких аккаунтах | Лимит живых представлений, ленивый старт, выгрузка неактивных |
